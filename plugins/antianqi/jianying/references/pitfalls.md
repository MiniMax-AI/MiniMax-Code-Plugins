# 踩坑清单（血买的，按"会不会再踩"排序）

> 每条都带**症状 → 根因 → 对策**。这清单是"经验层"，与 `verify-discipline.md`（判据）配套。

## 会静默出错的（最危险）

### 1. 节点参数形态不对 ⇒ 整段被跳过，链却"跑通了"
- **症状**：链输出正常，但少了某个节点的效果；探针里那个节点是 0
- **根因**：链 API 的键名/嵌套形态不匹配（各节点风格互不相同）
- **对策**：① 逐节点生效探针**内建在 `grade_apply` 动词里** ② 链 API 键名必须查 `references/chain-api.md` ③ 未知键**直接拒绝**（schema 硬校验）

### 2. `curves` 与 `hsl_curves` 的控制点布局不同
- **症状**：曲线形状怪、控制点不生效
- **根因**：`curves` 是 **A,L,R**；`hsl_curves` 是 **L,A,R**
- **对策**：看第一个三元组的第二项是 x 还是 y —— 是 x ⇒ A,L,R；是 y ⇒ L,A,R

### 3. 探针自己用错了 spec
- **症状**：多个节点报出**完全相同**的数
- **根因**：探针用了全局 spec 而非单节点 spec
- **对策**：**"数值整齐得不正常"就是探针没在测** —— 见到整齐输出先怀疑探针

## 编码 / 环境

### 4. 本机系统默认 GBK ⇒ Python 打印非 ASCII 就炸
- **症状**：`UnicodeEncodeError: 'gbk' codec can't encode character '³'`
- **对策**：脚本自身 `sys.stdout.reconfigure(encoding='utf-8')` + 调用方设 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1`
- ★ **skill 要做成"任何人调用都安全"**，不能只在自己 shell 里设环境变量

### 5. PowerShell 内联复杂 Python/JS 会被引号吃掉
- **症状**：语法错误、字符串被截断
- **对策**：复杂逻辑写成 `.py` / `.mjs` 文件再执行；文档批量替换也用脚本

## 流程 / 判据

### 6. 单帧抽样当判据
- **症状**：明明改动了却判 FAIL（或反过来假 PASS）
- **对策**：`verify_diff` 取全帧最大

### 6b. ★★ 拿"别的跑"留下的目录当基线（2026-10-21 实测）
- **症状**：自检显示 `maxMad=123.5 改动可见`，但那 123.5 根本不是这次改动造成的
- **根因**：自检把**另一次跑**的"改前帧"目录当基线，拿它和**这次**的"改后帧"比
  ⇒ 比的是两次不同的改动，PASS 与被测链路无关（**假绿**）
- **对策**：基线必须**本次自产**；自检开头就渲染自己的"改前"；`expect` 写死这次要验证的东西

### 6c. ★★★ 官方渲染器【不是确定性的】⇒ 裸像素阈值没有判别力
- **症状**：同一份草稿渲染两次，帧就变了（14~17/108 帧），最差 MAD **48~123**
  ⇒ 任何"max MAD > 0.5 ⇒ 改动可见"都是自说自话（噪声比阈值高两个数量级）
- **根因**：`jyai-b-render.mjs` 抓帧是"seek 后轮询 captureFrame，取容差内的第一帧"；
  抓哪一帧取决于调度时序 ⇒ 不确定。**收紧容差（60ms→20ms）也没用**（实测噪声依旧）
- **对策**：① 改草稿链用**语义判据**（落盘草稿的逐段字段差）② 像素判据必须传 `noiseDir` 做噪声校准
  ③ 我们自己的 GL/LUT 渲染链是确定性的，它的像素差分才可信
- **教训**：**报"改动可见"之前，先报噪声底。**

### 7. 两份验收并发跑写同一目录
- **症状**：证据互相污染，数字对不上
- **对策**：独立输出目录；文档写清目录名

### 7b. 用字符串收集 stdout 会毁掉二进制
- **症状**：两个**不同**的 PNG 序列比出"0 差异"
- **根因**：`so += d`（d 是 Buffer）⇒ 走 utf8 解码 ⇒ 非法字节被替换 ⇒ 不同数据塌成同一串
- **对策**：二进制必须用 `Buffer.concat(chunks)` 收集（插件的 `run()` 已用 `opts.binary`）
- ★ 我在 2026-10-21 的噪声探针里**又踩了一次**（自己写的探针假报"0 差异"）⇒ 写完探针先自问"它会不会假绿"

### 8. 写文档凭记忆
- **症状**：URL / 端口 / 管道名 / 白名单 / 计数写错
- **实测**：我把 bridge 端口编成 `4498`（代码里根本没有这个数）、把管道后缀说成"剪映主进程 pid"（实际是 `vebun.exe` 的 `ParentProcessId`）
- **对策**：写入前逐条对源码

### 9. 把官方的结构当我们的模板
- **症状**：照抄了一堆 mcode 根本不认的目录（`model/`、`model-tasks.json`…）
- **对策**：**官方是素材与语义的来源，mcode 规范才是结构约束**；先读 `docs/plugin-compatibility.md` 与 `node scripts/validate.mjs（仓库根，不是插件目录）`

### 10. "把 demo 当默认值的代码"= 没被测过的代码
- **症状**：spec 里没有某个节点 ⇒ `KeyError`
- **根因**：`path_A` 写死调用了 `sharpen`/`vignetting`
- **对策**：按 spec 动态跑；skill 第一次用"用户自己的 spec"就把它炸出来了

## 协议 / 通道

### 11. `player/load` 的 `workspacePath` 有两个含义
- **症状**：渲染出来"媒体丢失 / Media Not Found"红卡
- **根因**：`player/create→load` 路径要**草稿目录的父目录**；渲染路径要**草稿目录本身**
- **对策**：别混这两个调用

### 12. 音频的三个量纲坑
- **症状**：音量对不上 / 裁剪没生效
- **根因**：① 键名带点是**字面量**（`a['duration.ms']`，不是 `a.duration?.ms`）② `timeline.*.ms` 是**毫秒**、`attributes["duration.ms"]` 是**微秒** ③ `volume` 的量纲按段类型不同（`text_to_audio` 0..1 线性 / `sound` 0..100 百分比 / 视频段 0..1）
- **对策**：一律以 timeline 为准；ffmpeg 的 `atrim`/`afade` 要**秒**

### 13. 草稿搬过家 ⇒ `source` 是过期路径
- **症状**：素材找不到
- **对策**：按 basename 在 `<draftDir>/{video,audio}`、`<workspaceRoot>/{video,audio}` 回退查找

### 13b. ★ `jyai-live read --path` 少了 `--root` ⇒ 静默返回空（2026-10-21 实测）
- **症状**：`draft_read` 带 path 读指定草稿，返回 `exists=undefined cipherType=undefined chars=0`，**不报错**
- **根因**：官方 `draft/readFile` 要 `rootPath` 解析 workspace；`jyai-live read` 默认取 `st.draftDir`，
  而插件读的是**别的目录**（副本）⇒ 解析不出来 ⇒ 返回空
- **对策**：插件的 `draft_read` 现在**自动补 `--root`**（默认取 path 的上级目录）
- ★ 凡是"读别处的草稿"，先确认 root 传了没有 —— **静默返回空比报错更难发现**

## 渲染 / 数学

### 14. 3D LUT 表达不了邻域 / uv 依赖
- `sharpen`（邻域）· `vignetting`（uv）· `particle`（uv）· `clear`（金字塔）⇒ **只能渲染期算**

### 15. GPU float32 `fract` 在 ~1.2e4 量级不可复现
- **症状**：颗粒效果逐像素对不上（69.5% 像素接近，4.7% fract 整单位跳变）
- **结论**：实用无影响，不要在这上面耗时间

### 16. 官方 shader 的定点编码会截断
- `enCode` 的字节会溢出（|v|>1 时截断）⇒ 拉普拉斯差分超出 [−1,1] 会丢精度
- 对策：链内用 float64 复刻，别在中间丢

### 17. 官方某些效果默认就是空转
- `sharpen`：`white_gam`/`black_gam` 被注释掉
- `clear`：`intensity = self.intensity * sharpIntensity`，而 `sharpIntensity` 默认 **0** ⇒ 输出逐字节等于输入
- ⇒ **看到"官方效果没出来"，先查默认参数，不是我们的 bug**

## ★ 2026-10-22 审计新增

### 18. ★★★ 输入问题被误报成"链坏了"——三类都要分开报

同一个坑这轮出现了三次（"素材缺失""源画面全黑""音轨静音"），症状都是**明明链是好的，报错却说链坏了**：

| 症状 | 真实原因 | 该怎么说 |
|---|---|---|
| "成片文件过小/不存在" | 草稿素材不在磁盘上 ⇒ 官方渲出黑帧 ⇒ 3 秒纯黑 h264 只有 3 KB | 字节数只作**提示**；主判据 = **有视频流 + 时长对齐**；再加**首帧全黑检测** |
| "响度 −70 LUFS 偏离目标" | 音轨是**静音**（素材缺失），不是归一化坏了 | 响度 ≤ −60 LUFS 判为**静音**（输入问题）⇒ 报"音频素材缺失 N 个" |
| "★ 下列节点没有生效（探针为 0）" | 源画面**近乎全黑** ⇒ 加亮类调色被 clip 回 0 | 报"**源没有可测信息**，不是节点没生效"，并附源 YAVG |

⇒ **通用规则**：报"失败"前先分清 ①链真的坏了 ②输入本来就那样 ③参数写错了 ⇒ 三者用不同的话报。

### 19. ★★★ 探针只看第 0 帧 ⇒ 暗素材上误报

> `jyai-grade-render.py` 的逐节点生效探针原来只取 `frames[0]`。
> 实测：源首帧 YAVG=16/255（近黑）⇒ brightness 加 0.2 / 0.6 后被 clip 回 0 ⇒ 探针=0 ⇒ 误报"节点没生效"。
> ⇒ **改成多帧取最大**；全片都无信息时明确说"源画面近乎全黑，无法用亮度差判生效"。

### 20. ★★★ schema 声明了但后端不支持 ⇒ 静默忽略

> `draft_read` 的 `scope` 参数：schema 里有（还带 enum 校验，传非法值会报错），
> 但 **handler 根本没把它传给后端**，后端也不支持分段读 ⇒ 传合法值时**静默返回全量**。
> 而且 `SKILL.md` 里还教用户这么用 ⇒ 用户照做会拿到错的东西。
>
> ⇒ **要么真接上，要么从 schema 删掉**（schema 里的死参数比没有更糟，因为它看起来能用）。
> ⇒ 已删：schema 去掉 `scope`，SKILL 的示例改掉，并加了一条回归断言（传 scope 必须被拒）。

### 21. ★★ 删东西之前先查"有没有东西依赖它"

> 清理草稿库时把插件自检 e2e 依赖的两个草稿删了 ⇒ 9 条 e2e 全部 SKIP，
> 而自检计数仍然是"0 FAIL"⇒ **看着绿，其实没测**。
> ⇒ 删之前先扫一遍 tools/ 与 scripts/ 里对它的引用。
> ⇒ 配套：e2e 用例缺环境时必须**显式 SKIP 且不计入 PASS**。

### 22. ★ 跨副本比对内容必须忽略行尾符

> 已装副本是 git clone（有 `core.autocrlf` ⇒ 工作区 CRLF），PR worktree 是 LF
> ⇒ **sha256 逐文件比全是假差异**。⇒ 比对前统一行尾符（或直接看 `git log` / `git status`）。
> ⇒ 真正的"落后"要用 git 看，不是哈希看。

### 23. ★★ 官方预览渲染器的能力边界（实测，2026-10-22）

> 用**同源 5 稿对照**（噪声底精确为 0）量出来的：
>
> | 能力 | 官方预览渲染器 |
> |---|---|
> | 强度型调色（`materials.effects[]` 里 `type:"brightness"` + 段引用） | ✅ **它就带** |
> | 几何 / 合成（画中画 / alpha / 缩放） | ✅ |
> | 曲线 / HSL / 色轮 | ❌ |
> | 特效链（`materials.video_effects[]` / `materials.effects[]` 的 `mix_mode` 等） | ❌ |
> | `materials.placeholders[]` 的 `type:"adjust"` | ❌ |
> | forceRender 链 | ❌ |
> | 导出档渲染器 / 官方编码器 / 官方混音器 | ❌（在 app 内私有 mojo 通道后面） |
>
> ⇒ **所以"把调色写回剪映预览"只对强度型成立**；曲线类只能我们自己在出片链里做。

### 24. ★★★ 参数名拼错 ⇒ 烘出恒等 LUT（schema 与实现都不拦 ⇒ 出片"成功"但调色没发生）

> 实测（2026-10-22）：`make_film --grade '{"adjustColor":{"brightnessX":0.1}}'`
>
> | 层 | 表现 |
> |---|---|
> | schema | `make-film.schema.json` 里 grade 的每个节点只写了 `{type:object}` ⇒ **弱校验，放行** |
> | 实现 | 烘焙器 `normalize_chain_spec` 里 `adjustColor` 没有专门分支 ⇒ 原样透传给 `node_adjustColor` ⇒ 它只认自己那 11 个键 ⇒ `brightnessX` 被**静默忽略** |
> | 产物 | 产出的 cube 与【空 spec】的 cube **逐字节相同**（md5 `3abf7454…`）⇒ **恒等 LUT** |
> | 结果 | 出片"成功"、验收"通过"、**调色根本没发生** |
>
> ⇒ ★ **两层都要堵**：
> ① **schema 层**：`make_film` 的 `grade` 复用 `grade_apply` 的 spec 约束（跨动词复用，单一真源，零重复声明）
> ② **实现层**：烘焙器自己拒未知参数名 —— 这样**绕过 schema 直接调脚本**也堵得住
>
> ⇒ ★ **判据**：任何一次"某节点单烘"的结果都**必须非恒等**；
> **cube 与空 spec 逐字节相同 = 恒等 = 这个节点没生效**（比"看数值"更硬，不依赖渲染确定性）。

### 25. ★★★ 剪映的 session id 会【回收复用】⇒ 旧快照被当成新会话的草稿（实测，2026-10-24）

> **症状**：`draft_read {sessionId}` 读出来的草稿跟你刚 `draft_open` 的完全不是一份
> —— 段数、时长、草稿 id 全不一样；`draft_patch` 的 split"accepted 却什么都没变"。
> 最坑的一次：会话 155 读出来的竟是**两天前**（10-22）那个会话留下的草稿。
>
> **根因**：剪映进程重启后 session 计数**从 1 重新数** ⇒ id 被回收。
> 插件的状态目录里还留着上一次的 `snapshot-<sid>.json` ⇒
> 而 `draft_read` 是**优先读快照**的 ⇒ 于是新会话"继承"了旧草稿。
>
> **对策**：**`draft_open` 开新会话时，先把这个 id 的旧快照删掉**。
> 另加一道：会话状态里记下草稿 id，读到的 id 对不上就**点名报错**（不默默给一份别的草稿）。
>
> ⇒ **通用教训**：任何"按 id 缓存"的东西，都必须考虑 **id 会回收**。

### 26. ★★★ 官方 `draft/readFile` 在路径解析不出 workspace 时会【静默返回另一份草稿】

> **症状**：同一份草稿，有时读到 2 段 3 秒，有时读到 4 段 9 秒 —— 内容随时间变。
>
> **根因**：`readFile` 带 `rootPath` 时按路径解析；解析不出来时**不报错**，
> 而是返回**剪映当前打开的那份草稿**。副本目录（不在草稿库里）最容易踩。
>
> **对策**：① 副本目录要带对 `rootPath`（副本所在目录）②
> **关键判据一律用【会话快照】**（`draft_patch` 的响应写进去的，`draft_read` 优先读它），
> 不要拿"磁盘回落读"当基线 ③ 读到的草稿 id 与会话记录不一致 ⇒ 立刻停手。

### 27. ★★ 改前改后读到的【草稿形态】不同 ⇒ 比总时长比出的是误导（实测，2026-10-24）

> **症状**：`talk-cut-apply` 打印"时间线判定 ✗ 实际 3000000（期望 7933333）"，
> 而刀其实**落对了**（段确实被切成了两半）⇒ 假红。
>
> **根因**：磁盘上的草稿是**精简形态**（段 11 个键），官方返回的是**运行时展开形态**（段 50+ 个键）。
> 两种形态混着比总时长 ⇒ 比的是两件不同的东西。
>
> **对策**：判据必须**形态无关**。现在用的是
> **"这一轨的时长总量正好少了 (t1 - t0) us"** —— 只看段数与时长，形态无关。

### 28. ★★ 官方删除片段会把后面的段【左移补空】⇒ "区间不再被覆盖"是错的判据

> **症状**：明明删掉了中间段，回读却发现该区间又被别的段盖上 ⇒ 误判"没生效"。
>
> **根因**：`segment.delete` 之后，后续段整体前移补空 ⇒ 时间线保持连续。
>
> **对策**：判据改成 **"这一轨的时长总量少了恰好 (t1-t0)"**（位移不影响时长总量）。
> ⇒ 顺带：**别按轨道类型（video/audio）分组**，两个 video 轨道类型一样 ⇒ 要用**轨道 id**。

### 29. ★★ 探针的基线是【加密草稿文件】⇒ 读不出来 ⇒ 假阴性（实测，2026-10-24）

> **症状**：`draft_patch` 报 `effectVerified=false, changes=0`，
> 而实际段已经被切成了两半（`a1ac03@0+1500000 + C956BE38@1500000+1500000`）。
>
> **根因**：生效探针用 `readDraftJson` 读改前的基线；**草稿在盘上是加密封装** ⇒
> 解析失败返回 null ⇒ 探针以为"改前不存在" ⇒ **段数变化算不出来 ⇒ 说"什么都没变"**。
>
> **对策**：读不出就**走官方管道解密**（`readDraftForDiff`：先本地解析，再官方读）。
> ⇒ **通用教训**：判据的基线读不出来时，必须**换一条路读**，不能当成"没有基线"。

### 30. ★ 脚本步骤的参数键必须是【命令行 flag】⇒ 写错会静默用默认值（实测，2026-10-24）

> **症状**：`run_pipeline` 的脚本步骤跑通了，但脚本**根本没收到参数**（用了默认值）。
>
> **根因**：profile 里把参数写成对象键（`{"srt": "$srt"}`），
> 而脚本的 CLI 是 `--srt` ⇒ 脚本"不认识"这个键 ⇒ 静默走默认值分支。
>
> **对策**：① profile 里脚本步骤的键**必须写成 `--xxx`** ② 机械审计 **7n** 会把
> 每个脚本步骤的 flag 跟脚本源码里真实的 flag 对一遍，对不上就报。
> ⇒ **通用教训**：编排器把参数传给子进程时，**键的形态本身就是契约**，必须被校验。

### 31. ★★ 新增路线却忘了同步 schema 的枚举 ⇒ 路线【存在却调不动】（实测，2026-10-24）

> **症状**：往 `pipeline-profiles.json` 加了两条路线，审计全绿、文件也在，
> 可一调那条新路线就被拒：`args.profile: "subtitle-then-render" 不在允许集合 [...]`。
>
> **根因**：`run-pipeline.schema.json` 里 `profile` 是**枚举**，而枚举**手写**、
> 与 `pipeline-profiles.json` **没有任何对账** ⇒ 两份真源各说各话。
>
> **对策**：机械审计 **7k** 现在做【双向对账】——
> profile 里的每个 id 必须在 schema 枚举里，schema 枚举里的每个 id 也必须在 profile 里；
> 少一个就报 HIGH。负向注入 **㉜**（塞一条没同步枚举的路线 ⇒ 必须报）。
>
> ⇒ **通用教训**：**枚举也是契约**。凡是"从一份真源派生出来的清单"，
> 都要有一条机械检查把它们钉在一起，否则迟早漂。

### 32. ★★ 权重函数和它自己的注释自相矛盾 ⇒ 长词的优势被抹平（实测，2026-10-24）

> **症状**：加了"加字幕再出片"和"出片时把混音按草稿重做一遍"两句测试，
> 两条新路线都被**通用 skill 词**抢走（命中"加字幕"、"出片"）。
>
> **根因**：权重函数写的是"长词更具体 ⇒ 权重更高"，但实现是
> `len>=3 ? 3 : len==2 ? 2 : 1` ⇒ **所有 3 字以上的词权重都一样**（全是 3 分）
> ⇒ 一句命中"加字幕再出片"(6 字) 只得 3 分，
> 反而输给命中"加字幕"(3 分) + "字幕"(2 分) 的 skill 条目（5 分）。
>
> **对策**：权重**随长度增长**（`min(8, len)`）⇒ 长词才真的更重。
> 加完之后 33 句测试句 top-1 **100%**（原来 31 句时也是 100%，新加的两句一开始是 2/2 错的）。
>
> ⇒ **通用教训**：**注释说了什么 ≠ 代码做了什么**。
> 权重/阈值这类"语义规则"，必须有**跟注释一致的实现**，
> 否则注释会变成一句没人验证的漂亮话。

### 33. ★★★ "PASS" 不等于"全查过了" ⇒ 没判的维度必须点名（实测，2026-10-24）

> **症状**：单版审片跑完，`verdict: PASS`、`problems: []` ⇒ 看着像"全部通过"，
> 可实际上 `visibility` 维度根本没判（没有改前可比）。
>
> **根因**：`verify_diff` 把"跳过的维度"（`skipped`）只写进 `checks` 里，
> 不进结论 ⇒ 读结论的人只看到 PASS ⇒ **"没发现问题"被当成了"没有问题"**。
>
> **对策**：结果里新增 **`undetermined`**（列出没判的维度 + 原因）与 **`verdictNote`**
> （"有 1 个维度【未判定】（visibility） ⇒ 这不是'完整通过'；未测的维度要写成'待确认'，不能写成'正常'"）。
> ★ 这正是官方 `editing-review` 的纪律：**没有足够证据的必查项要保留为"待确认"**。
>
> ⇒ 顺带：**单版审片**（只给改后）现在也是一等公民：
> visibility 判不了 ⇒ 明说 skipped 并**给出噪声底**；picture 只给绝对值**不判失败**；
> audio / timeline / draft_integrity 照判。

### 34. ★★ 编排器"跑完了"但报告里看不到结论（实测，2026-10-24）

> **症状**：审片路线跑完 `verdict: PASS`，可**报告里一个审片数字都没有**。
>
> **根因**：编排器的步骤摘要只保留一份**白名单字段**，而 `verify_diff` 的结论在
> `checks` 里（不在白名单）⇒ 被丢掉了 ⇒ **路线跑成了，却没产出它该产出的东西**。
>
> **对策**：`verify_diff` 走**专用的紧凑摘要**（保留各维度关键数字，丢掉逐帧明细，
> 否则 `frameDetail` 会把报告撑爆）⇒ 并把 `undetermined` / `verdictNote` 一起带出来。
>
> ⇒ **通用教训**：**一条链的产出是什么，要和它的摘要机制对齐**。
> "跑成功"和"产出了结论"是两件事。

### 35. ★★★ 判据写成了"响度值本身"而不是"偏离目标的量"（实测，2026-10-24）

> **症状**：报告里自相矛盾 ——
> `"integratedLufs": -14` 与 `"响度未归一到 −14 LUFS"` 同时出现。
>
> **根因**：判据写成 `Math.abs(c.integratedLufs) > 0.5`
> ⇒ 它比较的是**响度值本身**（−14 的绝对值 = 14 > 0.5）⇒
> **任何正常归一到 −14 LUFS 的片子都会被说成"未归一"**。
>
> **对策**：判偏离量 `Math.abs(lufs − (−14)) > 0.5`。
>
> ⇒ ★ **通用教训**：*判据要比较"目标 vs 实测"，不是"实测 vs 0"*。
> 差一个括号，判据就从"有判别力"变成"永远报警"。
> ⇒ 而且这类 bug **不会让自检变红**（它只多了一句 note）⇒
> **只能靠人读报告发现** ⇒ 所以审片结论必须**逐条人眼过一遍**。

### 36. ★★ 一份路线里开两份草稿 ⇒ `$dir` / `$sessionId` 会被覆盖（实测，2026-10-24）

> **症状**：两版对照审片的第 2 步拿到了**改后**的副本目录，改前的副本"丢了"。
>
> **根因**：`draft_open` 总是把产出写进同一组变量（`$sessionId` / `$dir`）⇒
> 第二次调用把它们覆盖了。
>
> **对策**：编排器新增 **`setVars`**（`{"$dirBefore": "$dir"}`）
> —— 在**这一步之后**求值（抓的就是这一步的产出），值可以是变量引用或含 `$var` 的模板
> ⇒ 第一个副本先存成 `$dirBefore`，第二个再覆盖不迟。
> ⇒ 顺带：草稿 JSON 文件名按**步骤号**命名（`draft-<n>.json`）⇒ 读多份草稿不互相覆盖。
> ⇒ 审计守卫：`setVars` / `produces` 的目标变量与引用变量都必须在 `variables` 里声明；
> `produces` 的路径不许含 `..` 或绝对路径。

### 37. ★★ 产物路径只有"响应"知道 ⇒ 需要 `capture`（实测，2026-10-24）

> **症状**：`grade_apply` 的产物（10bit 成片）的**确切文件名**只有它的响应里知道
> （`out` / `outLut`）⇒ 编排器没法把它喂给下一步。
>
> **对策**：新增 **`capture`**（`{"$graded": "out"}`）——
> 在步骤**之后**从响应对象里取值当变量；**响应里没有这个字段 ⇒ 明确报错**
> （不静默塞 undefined）。
>
> ⇒ 至此编排器有三种"把东西往后传"的方式，各管一段：
>
> | 机制 | 时机 | 干什么 |
> |---|---|---|
> | `produces` | 步骤**之前** | 声明这一步的产物**路径**（相对 `$outDir`） |
> | `capture` | 步骤**之后** | 从**响应**里取一个值（只有响应知道的东西） |
> | `setVars` | 步骤**之后** | 给已有变量起别名 / 派生模板 |

### 38. ★★ JSON 里写 `+` 字符串拼接 ⇒ 解析失败（同一个坑栽了两次）

> **症状**：改了 `pipeline-profiles.json` 后，审计直接**崩栈**
> （`SyntaxError: Expected ',' or '}' after property value`），什么发现都出不来。
>
> **根因**：JSON **不支持**跨行字符串拼接，我在 `note` 字段里写了
> `"note": "前半" + "后半"` ⇒ 它是 JS 的写法，不是 JSON。
>
> **对策**：① `note` 写成单个字符串 ② **审计遇到坏 JSON 要报成一条发现而不是崩栈** ——
> 现在审计用 `readJson()` 包住解析，坏 JSON ⇒ 一条 HIGH 发现 + 继续跑别的检查
> （**审计工具不能因为被审对象写错就失能**）。
>
> ⇒ ★ 通用教训：*写机器可读配置时，"看起来像代码"的写法要格外小心*；
> ⇒ ★ **工具的失败方式也要设计**：崩栈 = 失能，报一条发现 = 还能继续查别的。
