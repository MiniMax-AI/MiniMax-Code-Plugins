MCode Overview

MiniMax Code (mcode) is an AI coding agent that runs in the terminal: it parses codebases, modifies files, runs commands and executes tests, and stores every unit of work as a resumable Session. The sections below cover its command-line surface, command set, configuration, extension mechanisms and permission model.

Three Usage Forms

All three forms share one in-process Runtime lifecycle:

mcode · Interactive TUI

Starts the interactive terminal interface, with Composer, session view, status line and slash commands.

mcode exec · Headless

Runs a single task without the TUI, for use from scripts and CI.

mcode acp · ACP

Runs as an Agent Client Protocol service over stdio, for editors that support ACP.

Installation

Requires Node.js >=22.19 <23 or >=24 <27:

bash
npm install -g @minimax-ai/code \
  --allow-scripts=@minimax-ai/code,better-sqlite3 \
  --registry=https://registry.npmjs.org/

Installation provides two commands, mcode and mcode-tools; mcode-tools is placed on PATH and needs no prior TUI launch. Uninstall with npm uninstall -g @minimax-ai/code, update with mcode update.

Quick Start

Common commands:

bash
mcode                      # start the TUI
mcode "task description"    # start with an initial task
mcode --continue           # resume the most recent Session in this workspace
mcode --session            # browse Sessions
mcode --session <id>       # open by ID
mcode --tui-mode fullscreen
mcode -m <provider/model>  # switch model for this Session only
mcode init                 # analyze the codebase and generate AGENTS.md
mcode exec "..."           # run one headless task
mcode exec review          # review staged/unstaged/untracked changes
mcode acp                  # run as an ACP service
mcode login / logout       # sign-in state (--region cn|global)
mcode update
mcode provider list|add|remove|test|use|set-minimax-key
mcode plugin list|add|remove|enable|disable|marketplace

See CLI, Headless & ACP for the full flag set.

How Runtime and clients divide the work

The three entry points render very different things—a terminal UI, a single headless task, and an external protocol server—but they share one in-process Runtime. The Runtime owns sessions, model calls, tools and permissions; a client only handles input and presentation.

That boundary is the adapter. Once the Runtime is up, a client receives exactly one thing: an adapter object, and it never reaches into the Runtime internals. The adapter speaks a Thrift-defined DesktopService contract under /minimax-desktop/api/v1/, with SSE for streaming responses.

So changing entry points does not mean swapping engines: config, permission mode, plugins and MCP servers in a given workspace are the same ones whether you start the TUI or exec. login / logout are the only commands that never create a Runtime at all.

mcode exec (Headless)

Runs a single task without starting the TUI:

bash
# Basic: just give it a sentence
mcode exec "Reply with OK only."

# Run against a different working directory
mcode exec --cwd ./repo "Summarize the structure of this directory."

# Attach a file to analyze (the file must be inside the workspace)
mcode exec --file ./error.log "Determine why this build failed."

# Structured output, for scripts
mcode exec --output-format json "Reply with OK only."

# Save the final answer to a file
mcode exec -o ./answer.md "Reply with OK only."

# Read the task from stdin — do not pass a prompt argument in this form
echo "Reply with OK only." | mcode exec --input -

Key Semantics

  • --input and the prompt argument are mutually exclusive: supplying both fails immediately with The prompt argument and --input cannot be combined. When reading from a pipe, pass only --input -.
  • A --file outside the workspace cannot be authorized interactively in headless mode and is rejected; move the file into the workspace or authorize it first.
  • Setting --max-steps too low returns limit_exceeded on tasks that need to read files. That is not a task failure — rerun with a larger limit.
  • --effort applies to this Run only and is independent of --model; the declared strength is validated before launch, and validation failure ends the process with a non-zero exit code. The override is not written back to the Session.
  • The --model provider/model#xhigh suffix is not a reasoning effort: the Runtime treats it as part of the model identity and the requested strength is dropped silently. Use --effort xhigh to apply an effort.
  • Relative paths for --diagnostics-dir resolve against --cwd, and an existing non-empty directory is rejected so that prior evidence is not overwritten.
  • JSON validation failure still returns failure and is not repaired automatically; --output-last-message saves successful results only.
  • Diagnostics are kept out of stdout; a write failure only warns and does not replace the original execution error.

mcode exec review

Reviews staged, unstaged and untracked local changes. It accepts --cwd, --model, --effort, --config, --permission, --timeout, --max-steps, --output-format and --output-last-message.

It is neither a plain prompt handed to the model nor an invocation of the built-in code-review Skill. It is a structured Review mode built into the Runtime:

  • Once the Run carries the review marker, the Runtime swaps in a dedicated review system prompt that requires read-only investigation, reporting only issues introduced by the change at hand, and re-verifying every finding against the current workspace.
  • Tools are restricted to read-only investigation; the prompt explicitly forbids modifying files or Git state, installing dependencies, committing, pushing or deploying.
  • While Review is active it forbids loading the code-review Skill or calling the code_review tool, so the outer review is not duplicated.
  • The result is returned as a fixed XML contract, so it can be parsed programmatically rather than read as free text.

/review in the TUI is the interactive entry to the same review engine. The code-review Skill is a general-purpose skill the model loads on its own judgement when it decides a review is needed — the two are not the same thing.

  • Flags may be placed before or after review; when both positions specify a value, the explicit value after review wins.
  • Session and input/output flags (--session, --continue, --input, --input-format, --file, --output-schema, --diagnostics-dir) apply to exec <prompt>; the review form uses the flags listed above.
  • Finding issues still returns exit code 0; a non-zero code is reserved for invocation, Runtime or review-protocol failures.
  • The default is inline mode (review completes within the current Turn); setting review.mode: subagent switches to a sub-agent.

mcode acp

bash
mcode acp

Starts an Agent Client Protocol service over stdin/stdout. ACP-capable editors and agent clients use it to create, load, continue and close mcode Sessions. The TUI, exec and ACP share one in-process Runtime lifecycle.

mcode provider

bash
mcode provider list
mcode provider test <provider-id>
mcode provider add --name Work --base-url https://example.com/v1 \
  --api-format openai-completions --model vision-model \
  --context-limit 128000 --output-limit 8192 --support-image --use
mcode provider remove <provider-id> --yes
mcode provider use <source>
mcode provider set-minimax-key
  • The API key is read from MCODE_PROVIDER_API_KEY or from the environment variable named by --api-key-env.
  • --use tests the first model first and saves it only on success, then selects it as the default; a failure is not saved. Without --use the entry can be saved first and tested later with /provider.
  • Token limits must be positive integers; --support-image declares image-input capability explicitly rather than inferring it from the model name.
  • Custom headers for third-party relays live under custom_provider.<id>.options.headers.

Installation Troubleshooting

npm 12 blocks install scripts / missing native SQLite dependency

Symptoms: the install log shows npm warn install-scripts; at launch you get Could not locate the bindings file, a missing better_sqlite3.node, or migration_failed.

Fix (keeping the same package name, version and registry):

bash
npm install -g @minimax-ai/code@latest \
  --registry=https://registry.npmjs.org/ \
  --foreground-scripts --ignore-scripts=false \
  --include=optional \
  --allow-scripts=@minimax-ai/code,better-sqlite3
  • Adding only --ignore-scripts=false does not substitute for npm 12 script authorization.
  • Launch mcode only after [MCode] Native SQLite check passed. appears.
  • Users who installed through the official Shell/PowerShell installer can simply rerun the original install command.

Input Disambiguation Rules

The Composer labels the current input as Prompt, Command, Shell or Skill, and indicates whether pressing Enter sends, executes or invokes it.

  • A no-argument command executes only when there is no body text after the command name (trailing whitespace is allowed). If body text is entered, the whole line is sent as an ordinary prompt. For example, /context is a command, while /context explain this project is an ordinary prompt.
  • Commands that accept arguments (such as /sessions [query]) are still treated as commands.
  • A Skill invocation such as /docs explain the API is displayed as a Skill call with instructions.

Actual Behaviour of /history, /fork, /rewind, /edit

These three share one "history change" interaction (available only when the session is idle):

CommandBehaviour
/fork Creates a sub-session from a past user message, leaving the current session and files unchanged
/edit Replaces that prompt and regenerates from here; later conversation and file changes are removed
/rewind Removes later messages; optionally leaving files untouched or also restoring safely recoverable file changes

Precondition: a Session must have been started or resumed; unavailable while a response is running (Stop the running response before changing Session history.).

Side Session (BTW) Read-Only Commands

/btw (alias /side) forks a temporary side session from the most recent committed session boundary; the main task keeps running uninterrupted. The side session inherits the main session history as a read-only context, carries the same tool permissions, and is instructed to make no changes unless explicitly asked.

Only the following commands are available in the side session view:

helpchangelogcontextstatususageexporttranscriptcopyparent

  • /parent (or Ctrl+/) switches between the side session and the main session view without ending either.
  • Side sessions are temporary: they do not appear in /sessions and are cleaned up automatically when switching Sessions.
  • Press Ctrl+C in an empty Composer to close and discard the side session.

custom-command renders the output of the external command named by tui.customStatusLine.command into the status line. Smallest useful configuration — command is the only required key:

yaml
tui:
  statusLine:
    - custom-command    # list the items you want, in order; custom-command is the external command
    - current-dir
  customStatusLine:
    command: ~/bin/my-status    # the only required key

Optional keys and their accepted values (keys you get wrong are silently dropped, no error is raised):

  • display: inline (same row as the status line, the default) or block (its own block).
  • position: above or below; only meaningful with block.
  • colorMode: plain or ansi.
  • maxLines: maximum lines to display.
  • timeoutMs: per-execution timeout.
  • intervalSeconds: polling interval.

The command's stdout becomes the status line content, so it should stay lightweight and avoid long blocking work.

Running Commands Directly in the Terminal

Entering !pwd or !git status in the Composer and pressing Enter runs it immediately in the current Session working directory, showing stdout, stderr and the exit code live. The input line shows Shell · Enter run.

  • The result of !command is passed to the model with the next message; the execution itself makes no model request.
  • !!command shows its output only in the TUI and does not send it to the model.
  • Both the output and the pending context retain the most recent 64 KiB characters; beyond that a truncation notice is shown.
  • Press Tab to request local completion (reads local directories only, does not call the model and does not execute the draft).
  • Each command starts an independent Shell; the effect of cd and export is limited to that command.
  • Commands run with the permissions of the current OS user; macOS uses Bash, Windows prefers PowerShell.

The tui Section

yaml
tui:
  terminalTitle: [status, session-name, app-name]
  notifications:
    when: unfocused
    method: auto
    events: [turn-complete, turn-failed, permission-required, question-required]

terminalTitle

  • Available items: status, session-name, app-name, project-name; they can be reordered or omitted.
  • Setting null or [] disables title updates.
  • Unknown items are ignored.
  • The terminal title takes the form Needs approval | Fix login | MCode; renaming or switching Sessions updates it.
  • Unnamed Sessions use the project name and a short Session ID.

notifications

KeyValuesDescription
whenunfocused / always / neverWhen to notify
methodauto / osc9 / osc777 / belNotification protocol
eventsEvent arrayOmitted = all four; [] = disabled
  • Notifications identify the Session and suppress duplicates; a completion notification waits for that Session's queue to drain.
  • auto uses the detected terminal notification protocol and falls back to the bell on failure.
  • Notifications are suppressed by default when the foreground window is known to be focused; when focus is unknown the behaviour is best-effort.
  • OSC notifications inside tmux require pass-through support from the outer terminal; method: bel is available as a fallback.
  • Configuration changes take effect after restarting mcode.

Memory and Other Switches

These switches have defaults that cut against intuition: memory, askUser and skillEvolve are all on by default, so turning them off takes an explicit enabled: false. Only memory.proactive is off by default.

defaults
memory:
  enabled: true      # true by default; set false to disable Memory
  proactive: false   # false by default; when on, the Agent writes memory proactively
  dailyDigest:
    enabled: false   # false by default

askUser:
  enabled: true      # true by default; setting false makes calls fail with ASK_USER_DISABLED

skillEvolve:
  enabled: true      # true by default

Memory has no TUI command entry point: there is no /memory in the command list. It is a background capability driven by configuration rather than something you invoke in the Composer; this plugin's memory section lives in the local ~/.minimax/config.yaml and applies to mcode itself, not to this plugin.

Network Proxy

HTTP_PROXY, HTTPS_PROXY, ALL_PROXY, NO_PROXY and their lowercase forms are read. NODE_USE_ENV_PROXY is not required. localhost, 127.0.0.1 and ::1 always connect directly.

bash
HTTPS_PROXY=http://127.0.0.1:7890 mcode

Interactive sessions, exec, update downloads and Matrix tool requests follow the same proxy rules.

Telemetry

All channels are off by default and must be enabled individually (telemetry.diagnostics and others). MCODE_DISABLE_TELEMETRY or DO_NOT_TRACK overrides every analytics channel.

Applying Configuration Changes

  • Most configuration takes effect after restarting mcode, in particular the tui section.
  • /reload inside the TUI reloads TUI configuration and Plugins.
  • After editing, /config is a convenient way to verify the effective values.

Actual Bash Tool Behaviour

  • Only exit code 0 counts as success; the result preserves the facts of exit, signal, timeout, cancellation and partial output.
  • Large output keeps the head and tail; the first-response text budget is 24 KiB, and a full log reference is given when persistence succeeds.
  • Foreground waiting: with a native task_output it waits up to 60 seconds, then returns a background task ID for the same command; the total command timeout defaults to 600 seconds with a ceiling of 600 seconds. Without task_output it stays in the foreground, defaulting to 120 seconds with a ceiling of 300 seconds.
  • task_output reads by byte offset; a successful read may still report a command failure.
  • The optional description affects only the TUI summary, not execution or permission checks.

Stopping a Conversation and Background Work

  • An explicit stop (such as pressing Esc in the TUI) cancels the background Bash commands and sub-agents owned by that conversation within the current process, including work derived from task_append continuations and their sub-turns. Completion notifications do not wake the conversation automatically.
  • Leaving a conversation with /clear or by switching Sessions stops the current turn and suspends the Goal and queued instructions, but background work keeps running.
  • Only locally owned running tasks are cancelled; tasks held by other Runtime processes are unaffected.

Plugins

The things that extend mcode fall into three categories, and they are not peers of one another. This section covers only the second: a plugin is a distribution container — a folder on disk plus a manifest. It is not a capability in its own right.

The easiest thing to get wrong: a MiniApp is distributed in plugin form — the official wording is "MiniApps are interactive apps packaged as MiniMax Plugins". But what they share is the distribution mechanism, not the category. The dividing line is three things: the mcode field in package.json, a miniapp/ payload root, and a Node entry. All three present means MiniApp; anything less is a normal plugin. See MiniApp.

Capability Units: Three Parts That Extend the Agent

Skill: a written method of working

A Skill is a set of instructions telling the Agent what to do first for a given task, which tools to use, and how to check the result. It adds no new tools — it just makes the Agent more consistent at a particular kind of work.

Once installed, call it in the TUI with /<skill name>. mcode ships 16 built-in Skills, and you can write your own inside a plugin.

MCP server: new tools for the Agent

MCP (Model Context Protocol) is an open protocol whose job is to give the Agent tools it can really call — a database, an internal API, a company system. It answers "what can the Agent do", not "how should the Agent work".

An MCP server declares which tools it offers; the Agent calls them and gets results back. See MCP configuration for the file format and fields.

Hook: a command that runs by itself at the right moment

A Hook is a command mcode executes automatically at a chosen moment, so you never run it by hand. Typical uses: "notify me when a reply finishes", "check before anything deletes a file".

Hooks are registered by a plugin. Event names come from Claude Code, so an existing Claude Code Hook configuration can be moved over as-is. See Hook details for the fields and registration format.

Plugins: the box that holds them

A plugin is a folder on disk: it contains a manifest at .minimax-plugin/plugin.json declaring which Skills, MCP servers, and Hooks it provides. For the person installing it, the point is that one install brings everything into place — no separate Skill install, no MCP wiring, no manual hook registration.

It has no runtime of its own — no resident process, no port of its own, just a declaration the Host reads over and over. Once installed and enabled it is assembled in every subsequent session, until you explicitly disable or remove it. For when each of the three kinds takes effect, see the lifecycle comparison.

What a Plugin Can Declare

A manifest can declare three capability units, each in its own field:

Capability unitManifest fieldAfter installing

All three are capabilities for the Agent. A plugin may also carry a MiniApp, but that is a different kind of thing: it brings its own runtime contract and is not "one of the things a plugin installs".

Installing & Managing Plugins

bash
# See what is installed and what can be installed
mcode plugin list --available

# Install one (<plugin-id> is the plugin identifier)
mcode plugin add <plugin-id>

# Turn off / turn back on without uninstalling
mcode plugin disable <plugin-id>
mcode plugin enable <plugin-id>

# Uninstall
mcode plugin remove <plugin-id>

# Browse installable plugins
mcode plugin marketplace

Running mcode plugin directly opens an interactive plugin manager, which is easier to drive with the arrow keys; inside the TUI use /plugins [filter].

Plugins come from two places: the official catalogue, and local plugin folders already discovered on your machine. --available lists only what can be installed. disable only switches a plugin off temporarily and does not delete it — remove is what uninstalls.

Hook Details: Registering One in a Plugin

A Hook is simply "a command that runs by itself at the right time". You write the command in your plugin and say when it should run; mcode then executes it every time that moment comes around.

The most common example: to get notified whenever a reply finishes, listen for the Stop event and point it at a small notification script. Event names come from Claude Code, so an existing Claude Code Hook configuration can be moved over as-is. Three source formats are supported: MINIMAX, CLAUDE and CODEX.

A Hook blocks mcode until it finishes, so only synchronous command handlers (type: "command") are supported. Writing async in the registration document is treated as unsupported.

The Registration Document

The manifest's hooks field accepts five forms: a string path, a { "path": "…" } object, an array of either, an inline registration document object (in which case sourcePath is recorded as <manifest>), and omission, in which case the default path is used when that file exists. The registration document envelope has two equivalent forms: an outer "hooks" key, or event names directly at the top level.

json
{
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "node \"${PLUGIN_ROOT}/scripts/notice.cjs\"",
        "timeout": 5
      }]
    }]
  }
}
FieldRequiredConstraints
typeYesAlways "command"
commandYesNon-empty string
commandWindows / command_windowsNoEffective on win32 only, taking precedence over command
timeoutNoInteger seconds, 1–10; default 5000 ms; ceiling 10000 ms
matcherNoAt event-group level; up to 256 characters; validated as described below
argsNoArray of strings; CLAUDE only; supplying it selects the exec form
shellNobash or powershell; CLAUDE only; ignored when args is present
ifNoTool predicate such as Bash(rm *); CLAUDE only; only for PreToolUse, PermissionRequest and PostToolUse
additionalContextLimitNoNon-negative safe integer; CODEX only; only for five events

timeout must be a whole number of seconds between 1 and 10; a decimal, 0, or anything above 10 invalidates the whole registration (HOOK_SCHEMA_INVALID). In the MINIMAX format, matcher cannot be left blank.

matcher validation proceeds as follows: * is always valid; UserPromptSubmit and Stop do not have their content checked; CODEX accepts only [A-Za-z0-9_|]+; other formats split on | or , with each branch required to match [A-Za-z0-9_.:/-]+ as a whole; otherwise a portable regular expression is required — only non-capturing groups (?:...) are allowed, and look-around, named groups, backreferences and dangling escapes are rejected, as is any atom with a repeated quantifier reaching four occurrences.

A single plugin may hold at most 64 executable handlers; the surplus records HOOK_HANDLER_LIMIT_EXCEEDED.

Command resolution: when args is present the exec form is used and no shell is involved; in MINIMAX, without args the system default shell is used, with shell: bash becoming bash -c and shell: powershell becoming pwsh; in CLAUDE the default on POSIX is sh -c, and on win32 Git Bash is preferred over PowerShell. The command form requires Node.js to be present on the Hook process's PATH.

The Hook process reads a single UTF-8 JSON object from stdin. Event-specific fields are expanded first, after which the following fixed keys are written:

json
{
  "hook_event_name": "PreToolUse",
  "session_id": "…",
  "turn_id": "…",
  "prompt_id": "…",
  "transcript_path": "…",
  "cwd": "…",
  "model": "…",
  "permission_mode": "…",
  "effort": { "level": "high" },
  "tool_name": "Bash",
  "tool_input": { }
}

turn_id, prompt_id, model, permission_mode and effort are absent when unset; transcript_path is null when no transcript exists yet; an input exceeding 1 MiB once serialized is not delivered. Time Budgets and Diagnostic Codes

The effective timeout of a single handler is the smaller of its declared value and the event's remaining budget. The total budget for ordinary events is 15 000 ms, for SessionEnd it is 3 000 ms, and the process drain window is 500 ms.

systemMessage: Shown to the User, Kept Out of Model Context

Write one JSON object to stdout and exit with code 0:

js
console.log(JSON.stringify({ systemMessage: "Checks complete. The report is ready." }));
  • It appears in the TUI as a Hook · Stop notice after the response.
  • It is excluded from canonical model history, compaction input, final-answer copying and the default Markdown export; it is written to local display storage.
  • Returning systemMessage alone does not trigger an additional model call.
  • Multiline text is supported; terminal control sequences in the message or title are stripped.
  • The notice colour is presentation only and does not indicate a failed turn.
  • The notice is persisted in Session display history and restored when the Session is reopened; replaying the same message does not duplicate it.
  • Separate Hook invocations may repeat the same text, each producing its own notice.
  • The notice belongs to the Session that produced it; a child Session's notice is not broadcast to the parent.

When control fields such as additionalContext or decision are returned alongside, those fields keep their existing per-event semantics. suppressOutput does not control this notice.

This is the script's output, not the Hook registration document itself.

Event Limits

  • The same display behaviour applies to the events for which the Runtime already emits notices: SessionStart / UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, SubagentStart / SubagentStop, and automatic PostCompact.
  • PreCompact and manual PostCompact currently emit no such notice.
  • SessionEnd delivery is best-effort and is not guaranteed to appear before exit.
  • The Claude-compatible adapter discards systemMessage for PreCompact, PostCompact and SessionEnd; the Codex adapter discards it for SessionEnd. These per-format differences are stable over time.
  • The above covers synchronous command Hooks only.
  • A cancelled or failed turn does not fire the normal Stop Hook.
  • Only categorized plugin user messages are shown; diagnostic messages, terminal-control notices and older events without a category remain hidden.
  • This behaviour concerns interactive TUI presentation only; headless and ACP output policies are unaffected.

MiniApp

A MiniApp is an interactive app with a UI that a person operates — not a tool the model calls. Once installed you open it on the desktop app and get an interactive page: a usage dashboard, a report, an approval panel.

MiniApps are a desktop-app feature only. The terminal build mcode has no such capability — mcode --help lists no miniapp command, which was confirmed by running it. mcode exec and ACP cannot use one either.

It is distributed in plugin form: copy the whole plugin directory (including the hidden .minimax-plugin/) into <data dir>/plugins/, restart the desktop app, then open it from the Mini App entry point. But "distributed as a plugin" is only its transport mechanism — it does not place it in the plugin category. For the dividing line, see the three kinds. The official community repository is MiniMax-AI/MiniMax-Code-MiniApps.

How MiniApp Differs from MCP

These two are easiest to confuse, because both "extend mcode". The difference is who uses them and how:

They are not mutually exclusive — a MiniApp can use MCP to fetch its data. The "Token Usage Board" in the official community repository is the textbook case: the panel itself is the MiniApp (charts for you to look at), while reading the local database is done by MCP or by a script the plugin ships. Put plainly: MCP fetches the data, the MiniApp shows it to a person.

Lifecycles: They Really Are Not One Kind of Thing

Plugins, MCP servers and MiniApps are easy to lump together, but their lifecycle mechanics barely overlap. Getting this wrong is what produces bugs like "why did my MiniApp lose its data on restart".

Plugin: effective as soon as it is installed

A plugin has no running process — it is a folder on disk. Once installed and enabled it is loaded in every subsequent session, until you explicitly disable or remove it. The enabled check happens every time capabilities are assembled, so a disabled plugin is never assembled.

When a plugin is activated it can raise SessionStart with the source plugin_activation. After editing a plugin, /reload re-reads it without restarting mcode.

The chain looks roughly like this:

MCP server: born with the Runtime, dies with it

An MCP server's lifecycle is tied to the Runtime: the Runtime reads configuration (<data dir>/mcp.json, <workspace>/.mcp.json, or a plugin's mcpServers), establishes the connection, and releases it when the Runtime ends.

  • stdio: the Host launches the server as a child process, which lives as long as the connection.
  • http / sse: connects to a remote service; the Host holds only the connection and starts no local process.
  • The child process inherits only 17 allowlisted environment variables (PATH, HOME, APPDATA, …) and no credentials; anything else must be declared explicitly in env.

MiniApp: started on demand, reclaimed when idle

MiniApp is the only one of the three that carries its own runtime. Its manifest declares runtime.lifecycle: on-demand: a Node process starts only when you open the page, and the Host assigns the port — you never pick one yourself.

  • Reference counting: each page view takes a lease; closing the page releases it. The Host waits for the lease count to reach zero before stopping.
  • Idle reclamation: with no leases left, an idle timer starts and eventually stops the process. So between two page views the process may well have been restarted.
  • Reuse is possible: the Host first tries to reuse a still-running instance; only an explicit forced start guarantees a new process.
  • Two-phase stop: stopping is a prepare-then-commit sequence, and a failed prepare rolls back instead of leaving you half-stopped.
  • Quarantine: on startup failure, or when cleanup ownership cannot be proven, the MiniApp is quarantined instead of being retried forever.

This is the trap people fall into: because the process can be reclaimed at any time, a MiniApp must not keep state in memory. The official guidance is explicit: "assume yours can be stopped and restarted between two page views: keep durable state in dataDir, not in memory". Anything that must survive is written to dataDir, a private directory the Host creates for each plugin.

dispose() may only close what the entry itself started — the HTTP server, timers, child processes, file and database handles. The Host stops the entry process only; it does not discover or terminate processes the entry spawned.

Writing a MiniApp

A MiniApp is, concretely, "a Node service plus a page, with a manifest". Here is the full structure and a minimal working implementation.

Layout

  package.json                  # Mini App declaration (below)
  icon.png                      # Plugin icon (PNG / JPEG / WebP)
  miniapp/

  README.md

  skills/<name>/SKILL.md        # Optional: also provides a Skill

  • name must match ^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$, at most 80 characters.

The Node entry: export start(context)

The Host imports runtime.entry as an ES module and requires a named export start. Return {dispose} — an object without dispose is rejected as an invalid lifecycle.

js
import { createServer } from 'node:http';
import { readFile } from 'node:fs/promises';
import { join } from 'node:path';

export async function start(context) {
  const { pluginRoot, dataDir, listen, signal, logger } = context;

  const server = createServer(async (req, res) => {
    // The page itself can be a single static HTML file
    const html = await readFile(join(pluginRoot, 'miniapp/client/index.html'));
    res.writeHead(200, { 'content-type': 'text/html; charset=utf-8' });
    res.end(html);
  });

  // Bind exactly the address the Host gives you; never pick your own port
  await new Promise((resolve) => server.listen(listen.port, listen.host, resolve));
  logger.info('miniapp ready');

  // Do not fetch business data inside start(): register handlers and resolve
  signal.addEventListener('abort', () => server.close());

  return {
    async dispose() {
      // Close only what you started: server, timers, child processes, handles
      await new Promise((resolve) => server.close(resolve));
    }
  };
}
context fieldMeaning
pluginIdThe plugin ID, i.e. plugin.json.name
pluginRootReal path of the installed package; read your client files from here
dataDirA private directory the Host creates and owns for this plugin; its location is opaque and may change. Put durable state here
listen{ host: "127.0.0.1", port } — bind exactly this address
signalAn AbortSignal that fires when the Host stops the MiniApp
loggerdebug/info/warn/error(message, fields?), messages truncated at 4 KiB. Only the keys of fields leave the process, so put diagnostic detail in the message
  • Never use console.log or process.stdout.write — stdout/stdin belong to the Host; log through context.logger.
  • Resolving start() is the readiness signal; there is no health route.
  • Vendor third-party runtime code inside the artifacts roots rather than relying on node_modules.
  • The official repository ships examples/hello-miniapp/ as a starting template, along with miniapp-api.ts type declarations (editor hints only; never imported at runtime).

Scope: this contract comes from the official repository MiniMax-AI/MiniMax-Code-MiniApps, which states it is verified against MiniMax Code desktop 3.0.73. The desktop app currently supports macOS and Windows; the terminal mcode covered by the rest of this manual does not provide MiniApps at all.

The Three History-Change Commands

CommandBehaviour
/forkCreates a sub-session from a past user message, leaving the current session and files unchanged
/editReplaces that prompt and regenerates from here; later conversation and file changes are removed
/rewindRemoves later messages; optionally "session only (files unchanged)" or "session and files (restoring safely recoverable file changes)"

Precondition: a Session must have been started or resumed; unavailable while a response is running (Stop the running response before changing Session history.).

Run Control

CommandEffect
/stopInterrupt the current turn
/queueManage messages that run after the current response; press c on a paused queue to resume from the head
/steer <message>Steer the current work without interrupting it
/tasksView background agents and Runtime tasks
/goal <objective | action>Start or manage the current Session Goal

Without an action, /goal takes the following text as the objective and creates or replaces the current Session's Goal. With an action it performs one of the following:

actionEffect
pausePause Goal auto-continuation
resumeResume a paused or blocked Goal
editEdit the current Goal objective
clearRemove the current Goal
helpShow Goal syntax and budget examples
budget=<n>Set a token budget; a value follows the =, for example budget=50K
budget=clearRemove the Goal token budget (back to unlimited)

Typing /goal in the Composer completes these actions. A Goal is active or paused; an absent budget means no token cap, and reaching a set cap ends the Goal through the normal termination flow.

Pressing Enter in the Composer steers the input into the current turn; Alt+Enter places it in the Queue for the next turn. The most recent queued message can be recalled with Alt+↑ (Option+↑ on macOS) or Shift+←.

Side Session (/btw)

  • /btw [question] (alias /side) forks a temporary side session from the most recent committed session boundary, and the main task keeps running uninterrupted.
  • The side session inherits the main session history as a read-only context, carries the same tool permissions, follows the current permission mode and adds no separate confirmation.
  • /parent or Ctrl+/ switches between the side session and the main session view without ending either.
  • Side sessions are temporary: they do not appear in /sessions and are cleaned up automatically when switching Sessions.
  • The switch shortcut only switches to an already-created side session and does not create one; before /btw has run it shows an amber notice.

Only read-only commands are available in the side session view: help, changelog, context, status, usage, export, transcript, copy and parent.
