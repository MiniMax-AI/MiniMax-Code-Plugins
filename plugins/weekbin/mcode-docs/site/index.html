MCode 概要说明

MiniMax Code（mcode）为运行于终端的 AI Coding Agent：解析代码库、修改文件、 执行命令、运行测试，每次工作保存为可继续的 Session。下文逐节说明其命令行界面、命令集、 配置、扩展机制与权限模型。

三种使用形态

三种使用形态共用同一个进程内 Runtime 生命周期：

mcode · 交互式 TUI

启动交互式终端界面，带 Composer、会话视图、状态栏与 slash 命令。

mcode exec · 无头 Headless

不启动 TUI，执行一次任务，供脚本与 CI 使用。

mcode acp · ACP

以 Agent Client Protocol 服务运行（stdio），供支持 ACP 的编辑器接入。

安装

要求 Node.js >=22.19 <23 或 >=24 <27：

bash
npm install -g @minimax-ai/code \
  --allow-scripts=@minimax-ai/code,better-sqlite3 \
  --registry=https://registry.npmjs.org/

安装同时提供 mcode 与 mcode-tools 两个命令；mcode-tools 无需先启动 TUI 即在 PATH 上。卸载用 npm uninstall -g @minimax-ai/code，更新用 mcode update。

快速开始

常用命令：

bash

Runtime 与 client 的分工

三个入口渲染的东西完全不同——TUI 是终端界面，exec 是无头跑一次任务，ACP 是对外的协议服务——但它们共用同一进程内的 Runtime。Runtime 负责会话、模型调用、工具与权限；client 只负责输入与呈现。

这条边界落在 adapter 上：Runtime 初始化后交给 client 的只有一个 adapter 对象，client 不直接触碰 Runtime 内部。它是一套 Thrift 定义的 DesktopService 契约，路径前缀 /minimax-desktop/api/v1/，流式响应走 SSE。

因此「换入口」不等于「换一套引擎」：同一个 workspace 里的配置、权限模式、插件与 MCP 在 TUI 和 exec 里是同一份。login / logout 不创建 Runtime，是唯一走不到这条边界的命令。

mcode exec（Headless）

不启动 TUI，直接执行一次任务：

bash
# 基本用法：直接给一句话
mcode exec "只回复 OK 两个字"

# 换一个工作目录
mcode exec --cwd ./repo "总结这个目录的结构。"

# 带上文件一起分析（文件需在 workspace 内）
mcode exec --file ./error.log "定位这次构建失败的原因。"

# 结构化输出，便于脚本处理
mcode exec --output-format json "只回复 OK"

# 把最终回答存到文件
mcode exec -o ./answer.md "只回复 OK"

# 从标准输入读取任务，此时不要再传提示词参数
echo "只回复 OK" | mcode exec --input -

关键语义

  • --input 与提示词参数互斥：同时给出会直接失败并报 The prompt argument and --input cannot be combined.。从管道读取时只写 --input -，不要再跟提示词。
  • --file 指向 workspace 之外的路径时，headless 无法弹交互授权，会被拒绝；把文件放进 workspace 或先授权。
  • --max-steps 给小了会在需要读文件的任务上返回 limit_exceeded，不是任务失败，换大步数重跑即可。
  • --effort 只对本次 Run 生效，与 --model 相互独立；启动前会按模型声明的强度校验，校验未通过即以非零退出码结束。覆盖不写回 Session。
  • --model provider/model#xhigh 后缀不是思考强度：Runtime 会把它当作模型身份的一部分，请求的强度被静默丢弃。需要强度生效请用 --effort xhigh。
  • --diagnostics-dir 相对路径基于 --cwd 解析，已有非空目录会被拒绝，避免覆盖前次证据。
  • JSON 校验失败仍返回失败，不会自动修复；--output-last-message 只保存成功结果。
  • 诊断不混入 stdout；写入失败只告警，不替换原始执行错误。

mcode exec review

只审查 staged、unstaged、untracked 的本地改动。仅支持：--cwd、--model、--effort、--config、--permission、--timeout、--max-steps、--output-format、--output-last-message。

它不是把一句话当提示词丢给模型，也不是调用 code-review 这个内置 Skill。它是 Runtime 内置的一套结构化 Review 模式：

  • 给 Run 打上 review 标记后，Runtime 换上一份专用的 review 系统提示词，规定只读调查、只报本次改动引入的问题、每条结论必须重新对照当前工作区核验。
  • 工具被限制在只读调查范围；提示词明确要求不得改文件、不得改 Git 状态、不得装依赖、不得提交或推送。
  • Review 生效后，禁止再加载 code-review Skill 或调用 code_review 工具，以免和外层审查重复。
  • 结果按固定 XML 契约返回，因此可被程序解析，而不是自由文本。

TUI 里的 /review 是同一套审查引擎的交互入口；code-review Skill 则是模型自行判断需要审查时才加载的通用技能，两者不是一回事。

  • 参数可放在 review 前后；两处都指定时以 review 后的显式值为准。
  • 会话与输入输出类选项（--session、--continue、--input、--input-format、--file、--output-schema、--diagnostics-dir）仅适用于 exec <prompt>，review 形式使用上列选项。
  • 发现问题仍返回退出码 0；只有调用、Runtime 或审查结果协议失败才返回非零。
  • 默认使用 inline 模式（当前 Turn 内完成审查）；显式配置 review.mode: subagent 时改用子代理。

mcode acp

bash
mcode acp

通过 stdin/stdout 启动 Agent Client Protocol 服务。支持 ACP 的编辑器与 Agent 客户端可借此创建、加载、继续和关闭 mcode Session。TUI、exec 与 ACP 共用同一进程内 Runtime 生命周期。

mcode provider

bash
mcode provider list
mcode provider test <provider-id>
mcode provider add --name Work --base-url https://example.com/v1 \
  --api-format openai-completions --model vision-model \
  --context-limit 128000 --output-limit 8192 --support-image --use
mcode provider remove <provider-id> --yes
mcode provider use <source>
mcode provider set-minimax-key
  • API Key 从 MCODE_PROVIDER_API_KEY 或 --api-key-env 指定的环境变量读取。
  • --use 先测试第一个模型，成功才保存并选为默认；失败不保存。不带 --use 可先保存后在 /provider 测试。
  • Token 上限必须是正整数；--support-image 显式声明图片输入能力，不凭模型名字猜测。
  • 第三方 relay 的自定义 header 位于 custom_provider.<id>.options.headers。

安装故障排查

npm 12 阻止安装脚本 / SQLite 原生依赖缺失

症状：安装日志出现 npm warn install-scripts；启动时报 Could not locate the bindings file、缺少 better_sqlite3.node，或 migration_failed。

修复（保持原包名、版本与 registry）：

bash
npm install -g @minimax-ai/code@latest \
  --registry=https://registry.npmjs.org/ \
  --foreground-scripts --ignore-scripts=false \
  --include=optional \
  --allow-scripts=@minimax-ai/code,better-sqlite3
  • 只加 --ignore-scripts=false 不能代替 npm 12 的脚本授权。
  • 看到 [MCode] Native SQLite check passed. 后再启动 mcode。
  • 通过官方 Shell/PowerShell 安装器安装的用户，重跑原安装命令即可。

输入判别规则（重要）

Composer 会把当前输入标记为 Prompt、Command、Shell 或 Skill，并提示按下 Enter 后是发送、执行还是调用。

  • 无参数的命令只在命令名后没有正文时执行（允许尾随空白）。如果继续输入正文，整句作为普通提示词发送。例：/context 是命令；/context 解释这个项目 是普通提示词。
  • 接受参数的命令（如 /sessions [query]）仍按命令处理。
  • Skill 调用形如 /docs 解释 API，会显示为带 instructions 的 Skill 调用。

侧会话（BTW）只读命令

/btw（别名 /side）从最近一个已提交的会话边界 fork 出临时侧会话，主任务继续运行不被中断。侧会话以只读上下文继承主会话历史，工具权限与主会话一致，并被要求除非明确请求否则不做修改。

侧会话视图中仅以下命令可用：

helpchangelogcontextstatususageexporttranscriptcopyparent

  • /parent（或 Ctrl+/）在侧会话与主会话视图间切换而不结束任何一方。
  • 侧会话是临时的：不出现在 /sessions 中，切换到其他 Session 时自动清理。
  • 空 Composer 中按 Ctrl+C 关闭并丢弃侧会话。

custom-command 把 tui.customStatusLine.command 指定的外部命令输出渲染到状态栏。最小可用配置——只有 command 是必填：

tui:

  customStatusLine:

终端内直接执行命令

在 Composer 中输入 !pwd、!git status，按 Enter 立即在当前 Session 工作目录执行，实时显示 stdout、stderr 与退出码。输入框显示 Shell · Enter run。

  • !命令 的结果随下一条消息交给模型；执行本身不发起模型请求。
  • !!命令 仅在 TUI 本地显示输出，不发给模型。
  • 两者输出与待发送上下文各保留最近 64 KiB 字符，超出显示截断提示。
  • 按 Tab 请求本地补全（只读本地目录，不调用模型、不执行草稿）。
  • 每条命令启动独立 Shell，cd 与 export 的效果仅限该条命令。
  • 命令以当前操作系统用户权限执行；macOS 使用 Bash，Windows 优先 PowerShell。

Bash 工具的真实行为

  • 退出码 0 才算成功；结果保留退出、信号、超时、取消与部分输出等事实。
  • 大输出保留首尾，首响应文本预算 24 KiB，持久化成功时给出完整日志引用。
  • 前台等待：有原生 task_output 时最多等 60 秒，之后返回同一命令的后台任务 ID；总命令超时默认 600 秒，上限 600 秒。无 task_output 时保持前台，默认 120 秒、上限 300 秒。
  • task_output 按字节偏移读取；一次成功读取也可能报告命令失败。
  • 可选的 description 只影响 TUI 摘要，不影响执行与权限检查。

停止对话与后台工作

  • 显式停止（如 TUI 中按 Esc）会取消该对话在当前进程内拥有的后台 Bash 命令与子 Agent，包括 task_append 续跑及其子回合派生的工作。完成通知不会自动唤醒对话。
  • 用 /clear 或切换 Session 离开对话时，会停止当前回合并暂停 Goal 与排队指令，但后台工作继续运行。
  • 只取消本地拥有的运行中任务；由其它 Runtime 进程持有的任务不受影响。

扩展 mcode 的东西分三类，类别不同，不能当成同一层的概念并列。本节只讲第二类：插件是分发容器——磁盘上的一个文件夹加一份清单，它本身不是一种能力。

最容易搞混的地方：MiniApp 确实以插件形态分发——官方原话是「MiniApps are interactive apps packaged as MiniMax Plugins」。但共享的是分发方式，不是类别。判定分界看三样东西：有没有 package.json 里的 mcode 字段、有没有 miniapp/ 载荷根、有没有 Node 入口。三样齐全的是 MiniApp，缺省的才是普通插件。详见 MiniApp。

能力单元：扩展 Agent 的三种零件

Skill：一套写好的工作方法

Skill 就是一份说明书，告诉 Agent「遇到这类任务，先做什么、用哪些工具、怎么检查结果」。它不新增任何工具，只是让 Agent 在特定任务上更专业、更一致。

装好后直接在 TUI 里用 /<skill 名> 调用。mcode 自带 16 个 Skill，也可以自己写一个放进插件里。

MCP 服务器：给 Agent 接上新的工具

MCP（Model Context Protocol）是一个开放协议，作用是给 Agent 增加可以真正调用的工具：连数据库、连内部 API、连公司系统。它对应的是「Agent 能做什么」，而不是「Agent 知道怎么做」。

一个 MCP 服务器在配置里声明自己提供哪些工具，Agent 调用后拿到结果。配置与字段见 MCP 配置。

Hook：到点自动跑的一条命令

Hook 是「在某个时机自动执行的一条命令」，你不用每次手动运行。典型用途是「每次回答结束发个通知」「每次要删文件前先检查一下」。

Hook 依附于插件注册：事件名取自 Claude Code，所以已有的 Claude Code Hook 配置可以直接迁过来。字段与注册方式见 Hook 详解。

插件：装东西的盒子

插件就是磁盘上的一个文件夹：里面有一份清单 .minimax-plugin/plugin.json，声明自己提供哪些 Skill、哪些 MCP 服务器、哪些 Hook。对使用者来说，它的意义是一次安装，全部就位，不用分别去装 Skill、配 MCP、挂 Hook。

它没有自己的运行时——不常驻进程、不占端口，只是一份被宿主反复读取的声明。装好并启用后，后续每个会话都会装配它，直到你显式 disable 或 remove。三类东西的生效时机对比见 生命周期对比。

Hook 详解：在插件里注册

Hook 就是「到点自动执行的一条命令」。你在插件里写好一条命令，再指明它在什么时候跑，mcode 每次遇到那个时机就会执行它。

举个最常见的例子：想让每次回答结束后都收到通知，就监听 Stop 事件，指向一个发通知的脚本。事件名取自 Claude Code，因此已有的 Claude Code Hook 配置可以直接迁过来；来源格式支持 MINIMAX、CLAUDE、CODEX 三种。

Hook 会在 mcode 等待它跑完之前阻塞后续流程，所以只支持同步的命令型处理器（type: "command"）。写注册文档时即使写了 async，也会被判为不支持。

注册文档

manifest 的 hooks 字段接受五种形式：字符串路径、{ "path": "…" } 对象、上述两者的数组、内联注册文档对象（此时 sourcePath 记为 <manifest>），以及省略时按默认路径自动纳入。注册文档的信封有两种等价写法：外层带 "hooks" 键，或直接以事件名为顶层键。

json
{
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "node \"${PLUGIN_ROOT}/scripts/notice.cjs\"",
        "timeout": 5
      }]
    }]
  }
}
字段必需约束
type是恒为 "command"
command是非空字符串
commandWindows / command_windows否仅 win32 生效，优先于 command
timeout否整数秒，取值 1–10；缺省 5000 ms；上限 10000 ms
matcher否事件分组级；上限 256 字符；校验规则见下
args否字符串数组；仅 CLAUDE；给出即采用 exec 形式
shell否bash 或 powershell；仅 CLAUDE；args 存在时忽略
if否工具谓词，形如 Bash(rm *)；仅 CLAUDE；仅 PreToolUse／PermissionRequest／PostToolUse
additionalContextLimit否非负安全整数；仅 CODEX；仅 5 个事件

timeout 要写成 1–10 的整数秒；写成小数、0 或超过 10 都会让整条注册无效（报 HOOK_SCHEMA_INVALID）。MINIMAX 格式下 matcher 不能留空。

matcher 校验依次为：* 恒合法；UserPromptSubmit 与 Stop 不校验内容；CODEX 仅接受 [A-Za-z0-9_|]+；其余格式以 | 或 , 分支，每支须整体匹配 [A-Za-z0-9_.:/-]+；否则按可移植正则校验——仅允许非捕获组 (?:...)，拒绝环视、命名组、反向引用与悬空转义，且同一原子重复量词达 4 次即拒绝。

单个插件可执行处理器至多 64 个，超出部分记 HOOK_HANDLER_LIMIT_EXCEEDED。

命令解析：存在 args 时走 exec 形式，不经 shell；MINIMAX 无 args 时经系统默认 shell，shell: bash 转为 bash -c，shell: powershell 转为 pwsh；CLAUDE 在 POSIX 下默认 sh -c，win32 下优先 Git Bash，否则 PowerShell。command 形式要求 Hook 进程的 PATH 上存在 Node.js。

MiniApp

MiniApp 是给人操作的有界面应用，不是给模型调的工具。装好后在桌面端打开就是一个可交互的页面——比如用量看板、报表、审批面板。

MiniApp 只在 MiniMax Code 桌面端提供，终端版 mcode 没有这个能力（mcode --help 中无 miniapp 相关命令，实测确认）。它是桌面端概念，mcode exec 与 ACP 同样用不到。

它以插件形态分发：把整个插件目录（含隐藏的 .minimax-plugin/）放进 <数据目录>/plugins/，重启桌面端后从 Mini App 入口打开。但「用插件分发」只是它的运输方式，不代表它属于插件那一类——判定分界见 三类东西。官方社区仓库是 MiniMax-AI/MiniMax-Code-MiniApps。

这两个最容易混，因为它们都是「扩展 mcode 的东西」。区别在谁在用、怎么用：

生命周期：三者确实不是一类东西

插件、MCP 服务器、MiniApp 最容易被当成同一类东西，但它们的生命周期机制几乎没有共同点。混淆这一点会直接导致「为什么我的 MiniApp 重启后数据没了」这类问题。

插件：装上就一直生效

插件本身没有运行中的进程，它就是磁盘上的一个文件夹。装好并启用后，它在后续每个会话里都被加载，直到你显式 disable 或 remove。启用状态的判定发生在每次装配能力时，禁用的插件不参与装配。

插件被启用或激活时，可以触发 SessionStart 事件，来源标识为 plugin_activation。改完插件内容后用 /reload 重载，不必重启整个 mcode。

整条链路大致是这样：

MCP 服务器：随 Runtime 建立，随 Runtime 结束

MCP 服务器的生命周期绑在 Runtime 上：Runtime 读配置（<数据目录>/mcp.json、<workspace>/.mcp.json 或插件的 mcpServers）后建立连接，Runtime 结束时一并释放。

  • stdio：宿主把服务器作为子进程拉起，进程随连接建立而存在。
  • http / sse：连远程服务，宿主只保持连接，不在本地起进程。
  • 子进程只继承 17 个白名单环境变量（PATH、HOME、APPDATA 等），不继承任何凭据；所需变量须在 env 中显式声明。

MiniApp：按需启动，空闲即回收

MiniApp 是三者中唯一自带独立运行时的：它在清单里声明 runtime.lifecycle: on-demand，打开页面时才启动一个 Node 进程，端口由宿主分配而不是自己挑。

  • 引用计数：每次打开页面会领一个「租约（lease）」，关闭页面即释放；宿主要停进程时先等租约归零。
  • 空闲回收：没有租约时启动空闲计时器，到点把进程停掉。所以两次打开之间进程完全可能已经重启过。
  • 可能被复用：宿主会先尝试复用仍在运行的实例，只有被显式强制启动时才一定新起进程。
  • 两阶段停止：停止不是一个动作，而是「准备 → 提交」，准备阶段失败可以回滚，不会把你停在半路。
  • 隔离：启动失败或清理责任无法确认时，该 MiniApp 会被隔离（quarantine）而不是反复重启。

这条最容易踩坑：因为进程随时可能被回收，MiniApp 不能把状态存在内存里。官方明确要求「assume yours can be stopped and restarted between two page views: keep durable state in dataDir, not in memory」。需要跨次打开保留的内容一律写 dataDir（宿主为每个插件创建的私有目录）。

另外 dispose() 只能关掉入口自己启动的东西（HTTP 服务器、定时器、子进程、文件句柄）；宿主要停的只是入口进程，不会替你清理它派生的那些进程。

MiniApp 怎么写

写一个 MiniApp 本质上是「写一个带清单的 Node 服务 + 一张页面」。下面是完整结构与最小可用实现。

目录结构

bash
<plugin-id>/
  .minimax-plugin/plugin.json   # 插件清单:身份、图标、分类、声明的能力
  package.json                  # MiniApp 声明(下面给出)
  icon.png                      # 插件图标(PNG / JPEG / WebP)
  miniapp/
    miniapp.json                # 载荷根目录、Node 入口、页面路由
    client/                     # 运行时载荷:发给页面的文件
    node/                       # 运行时载荷:Node 入口及其依赖
  README.md
  LICENSE
  skills/<name>/SKILL.md        # 可选:同时提供 Skill
  *.mcp.json                    # 可选:同时提供 MCP 服务器
  bindings/<name>.binding.json  # 可选:宿主能力绑定
  • 目录名必须等于 plugin.json 里的 name，且全仓库唯一（安装时作者目录会被丢掉）。
  • name 需匹配 ^[a-z][a-z0-9]*(?:[._-][a-z0-9]+)*$，最长 80 字符。
  • 只有 artifacts 里列出的 client/ 与 node/ 会成为运行时载荷，测试与文档要放在 miniapp/ 之外。
  • 包体上限：最多 1024 个文件、单文件 16 MiB、总计 64 MiB；不允许符号链接与硬链接。
  • 路径必须可移植：仅 ASCII、无 \、无 ./.. 段、不以 . 结尾。

package.json：声明这是一个 MiniApp

关键就是这个 mcode 字段，它把普通插件升级为 MiniApp：

    "miniApp": "./miniapp/miniapp.json"

miniapp/miniapp.json：入口与路由

json

  "artifacts": {

    "node": ["./miniapp/node"]

字段规则
artifacts.client / artifacts.nodeminiapp/ 下的非空路径数组，必须存在且唯一；这两项就是被哈希与安装的全部内容，node_modules 会被排除

Node 入口：导出 start(context)

宿主用 ES module 导入入口，并要求具名导出 start。返回 {dispose}，没有 dispose 会被判为非法生命周期。

js
import { createServer } from 'node:http';
import { readFile } from 'node:fs/promises';
import { join } from 'node:path';

export async function start(context) {
  const { pluginRoot, dataDir, listen, signal, logger } = context;

  const server = createServer(async (req, res) => {
    // 页面本身可以就是一个静态 HTML
    const html = await readFile(join(pluginRoot, 'miniapp/client/index.html'));
    res.writeHead(200, { 'content-type': 'text/html; charset=utf-8' });
    res.end(html);
  });

  // 必须绑定宿主给的地址，不要自己挑端口
  await new Promise((resolve) => server.listen(listen.port, listen.host, resolve));
  logger.info('miniapp ready');

  // 不要在 start 里拉业务数据：注册好处理器就返回
  signal.addEventListener('abort', () => server.close());

  return {
    async dispose() {
      // 只关你自己启动的东西：服务器、定时器、子进程、文件句柄
      await new Promise((resolve) => server.close(resolve));
    }
  };
}
context 字段含义
pluginId插件 ID，即 plugin.json.name
pluginRoot安装后的包真实路径，页面文件从这里读
dataDir宿主为本插件创建的私有目录，位置不透明且可能变化；持久状态写这里
listen{ host: "127.0.0.1", port }，必须绑这个地址
signal宿主停止 MiniApp 时触发的 AbortSignal
loggerdebug/info/warn/error(message, fields?)，消息截断 4 KiB；只有 fields 的键会离开进程，值留在本地，诊断细节写进 message
  • 不要用 console.log 或 process.stdout.write——stdout/stdin 归宿主所有，一律走 context.logger。
  • start() resolve 之后才算就绪，没有健康检查路由。
  • 第三方运行时代码要直接放进 artifacts 目录内，不要依赖 node_modules。
  • 官方社区提供 examples/hello-miniapp/ 作为起步模板，并附 miniapp-api.ts 类型声明（仅供编辑器提示，运行时不导入）。

适用范围：以上契约由官方社区仓库 MiniMax-AI/MiniMax-Code-MiniApps 给出，自述验证于 MiniMax Code 桌面端 3.0.73。桌面端目前支持 macOS 与 Windows；本手册其余部分覆盖的终端版 mcode 并不提供 MiniApp 能力。

  • 侧会话是临时的：不出现在 /sessions 中，切换 Session 时自动清理。
  • 切换快捷键只切换已创建的侧会话，不会创建侧会话；尚未执行 /btw 时会黄色提示。

侧会话视图中只有只读命令可用：help、changelog、context、status、usage、export、transcript、copy、parent。
