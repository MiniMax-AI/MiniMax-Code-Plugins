# customize：画像与规则修改入口

## 目的

docs/guardrails.md 的执业画像驱动所有技能的行为档位（见 docs/guardrails.md"画像如何驱动技能行为"
速查表）。直接手改画像的问题是：修改者往往意识不到一个字段牵动的下游行为——
例如把角色从"企业法务"改成"执业律师"，保密标头档位和 UPL 门控会同时变化。

本技能把修改收敛为一个有确认、有影响提示、有记录的流程，保证画像始终是
"被理解后的修改"的结果。

## 前置检查

1. 读取`docs/guardrails.md`，确认画像章节存在；
2. 如果画像仍大面积为 `[填空]`，提示：这不是修改而是初始化，应先跑
   `cold-start-interview`，除非使用者明确只要补一两个字段；
3. 确认 docs/guardrails.md 自上次读取以来未被其他进程改动（修改记录注释是最新
   一条）——多人共用工作区时，防止基于旧版本的画像做覆盖式写回；
4. 明确使用者要改的是哪一类：
   - A 类：画像字段（角色、法域、行业、业务、红线、升级矩阵、签署流程、
     数据源、输出偏好）；
   - B 类：Shared guardrails 正文（高影响，需额外确认）；
   - C 类：数据源凭证（实际配置在环境变量，本技能只更新画像中的记录，
     并指引配置方法）。

## 操作规程

### 1. 读出现状

把使用者要改的字段当前内容原样读出来，逐字复述给使用者。不凭记忆复述，
必须基于本次读取的 docs/guardrails.md 内容。

### 2. 确认修改意图

对每一项修改，向使用者确认三要素：

- 改什么：原内容 → 新内容（并排展示）；
- 为什么改（一句话即可，写入修改记录）；
- 是否理解行为影响（见第 3 步的影响提示，确认后再写入）。

涉及角色变更（律师 ↔ 非律师）时，必须额外说明：这将改变所有产物的保密
标头档位，以及是否启用 UPL 动作闸门，并要求显式确认。

### 3. 影响提示

修改写回前，按下表提示受影响的行为，逐条念给使用者：

| 修改字段 | 受影响行为 |
| --- | --- |
| 使用者角色 | G4 保密标头档位；G5 UPL 门控启停 |
| 所在法域 | G3 默认锚定；LEGAL_FRAMES 引用 |
| 行业与业务领域 | 监管规则适用性判断 |
| 常做合同类型 | 审查类技能的类型化清单调用 |
| 红线条款 | 审查命中提示；严重度下限 |
| 升级矩阵 | 停止推进与移交 brief 的触发条件 |
| 签署流程 | 签署要素核对与动作闸门提示 |
| 数据源凭证 | legal-research 源选择与覆盖缺口声明 |
| 输出偏好 | 篇幅、排版、语言 |
| Shared guardrails | 全部技能（最高影响，需逐条确认） |

### 4. 写回

- 只改使用者确认的字段，其余内容原样保留；
- 画像部分保持散文体，不得写成 YAML 字段；
- 写回后复读修改后的段落给使用者确认；
- 在 docs/guardrails.md 文末"维护说明"后追加一行修改记录：
  `<!-- customize: YYYY-MM-DD 修改{字段}：{原因一句话} -->`（注释形式，
  不影响正文阅读，便于追溯）。

### 5. B 类修改（guardrails）的额外要求

- 逐条展示拟修改的 guardrail 原文与新文；
- 说明"各 skill 正文可重复 guardrails 条目；冲突时以 docs/guardrails.md 本节为准"，
  因此修改会立即影响所有技能；
- 如果新规则比旧规则**更宽松**（例如降低某类提示的强制程度），必须显式
  提示风险并要求二次确认；更严格的修改一次确认即可；
- 修改 guardrails 后，建议使用者复核相关 skill 正文中转述的对应条目。

### 6. C 类修改（数据源）的额外要求

- 实际 token 配置在使用者的环境变量中，本技能不代设环境变量，只：
  1. 指引配置方法（指向 `references/connectors.yaml` 中对应 connector 的
     凭证说明）；
  2. 建议配置后运行 `cold-start-interview --check-integrations` 体检；
  3. 更新画像"常用数据源与凭证配置"小节的记录；
- 绝不询问、记录、打印 token 的具体值。

### 7. 操作纪律

- 一次只处理使用者明确提出的修改；不"顺手优化"其他字段；
- 写回前必须完成第 2 步的确认，禁止先写后问；
- 每次修改都有注释形式的修改记录，保证画像的演变可追溯；
- 修改失败（如文件写入异常）时，报告已完成的动作与未完成的部分，
  不留半改状态——docs/guardrails.md 要么完整写回，要么保持原样。

## 输出模板

```
修改确认
| 字段 | 原内容 | 新内容 | 影响 |
| --- | --- | --- | --- |
| {字段} | {原} | {新} | {受影响行为} |

以上修改已写回 docs/guardrails.md（{时间}）。
{如为角色变更或 guardrails 修改：本修改影响所有后续产物，请注意。}
```

## 常见修改场景示例

- **"我刚通过实习考核，正式执业了"**：角色由非律师改为执业律师。
  影响提示：保密标头从研究备忘档切到内部法律分析档；UPL 动作闸门关闭。
  需二次确认，因为标头档位变化影响所有后续产物。
- **"公司新规定，100 万以上合同要法务总监审批"**：审批底线新增一条。
  影响提示：审查类技能命中金额阈值时会停止并提示升级。
- **"我们配置了北大法宝"**：数据源记录更新。本技能不代设环境变量，
  指引使用者设置 PKULAW_SERVICE_ID 与 PKULAW_TOKEN 后运行
  `scripts/enable_pkulaw.py`（握手验证通过才写入配置），
  再运行 `cold-start-interview --check-integrations` 体检，确认后写回画像。
- **"以后输出都给我中英对照"**：输出偏好修改。影响提示：不改变
  guardrails 强制内容（标头、标注、分级），只改排版与语言。

## 本技能不做什么

- 不做首次画像初始化（那是 `cold-start-interview`）；
- 不设置或修改环境变量本身；
- 不回答法律问题；
- 不修改 `LEGAL_FRAMES/` 基线文件与 `references/` 参考文件（那些属于插件
  内容维护，不在画像定制范围）；
- 不批量"优化"画像措辞——只执行使用者明确要求的修改，避免无声漂移。

## 收尾与下一步

- 写回后复读新内容并获得确认；
- 角色变更后，提醒使用者下一份产物将按新档位加标头；
- 数据源变更后，建议跑一次 `cold-start-interview --check-integrations`；
- 修改涉及红线或升级矩阵的，提醒使用者：进行中的事项（matters/ 下 open
  状态）可能需要按新底线重新过一遍，可用 `matter-workspace` 查看在办事项。
